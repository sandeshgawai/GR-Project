# Fix Supabase persistence for e-GR Store

## Context

The app is wired end-to-end for a Supabase KV backend, but it silently runs in **Local** mode. The user believes the *deploy* is failing because there are "no migrations or tables." That is a misdiagnosis:

- **Deploying an edge function never runs SQL and never requires a table.** A missing table produces *runtime* 500s, not a deploy failure.
- The real gap: the `index.tsx` currently in the repo only implements `GET /health`. The five CRUD routes the frontend calls (`GET /grs`, `POST /grs`, `POST /grs/bulk`, `PUT /grs/:id`, `DELETE /grs/:id`) are **not present** — the earlier "self-contained" edits are not in the working tree. So after a clean deploy, `api.list()` (`GET /grs`) 404s, `src/store.tsx` catches the error and sets `backend = "offline"`, and the pill shows "Local".

Intended outcome: implement the missing routes so a deploy makes the app flip to **Database** mode with server-side persistence, and give the user a clear path to create the KV table if it isn't auto-provisioned.

## Files & contract (verified)

- `src/api.ts` — route prefix `make-server-210cf10a`; `list()` expects `{ grs: GR[] }` from `GET /grs`; `create` POSTs a `GR`; `bulk` POSTs `{ grs: GR[] }`; `update` PUTs a `GR` to `/grs/:id`; `remove` DELETEs `/grs/:id`. Auth header is `Bearer <anon key>`.
- `src/data.ts` — `GR` has a string `id` (plus `number`, `date`, `department`, `category`, `subject`, `keywords[]`, `description`, `status`, `important?`).
- `supabase/functions/server/kv_store.tsx` — **autogenerated, do not edit.** Exports `set/get/del/mset/mget/mdel/getByPrefix` against table `kv_store_210cf10a`.
- `supabase/functions/server/index.tsx` — the only file to change.

## Plan

### 1. Rewrite `supabase/functions/server/index.tsx`

Keep the existing Hono + CORS + logger scaffold and the `/health` route. Import the KV helpers via the standard pattern `import * as kv from "./kv_store.tsx"` (relative imports inside the function dir are fully supported — do **not** inline the KV code; `kv_store.tsx` is autogenerated). Add all routes under the `/make-server-210cf10a` prefix:

- `GET /make-server-210cf10a/grs` → `kv.getByPrefix("gr:")` → `c.json({ grs })`.
- `POST /make-server-210cf10a/grs` → read `GR` body → `kv.set(\`gr:${gr.id}\`, gr)` → `c.json({ ok: true })`.
- `POST /make-server-210cf10a/grs/bulk` → read `{ grs }` → `kv.mset(grs.map(g => \`gr:${g.id}\`), grs)` → `c.json({ ok: true })`.
- `PUT /make-server-210cf10a/grs/:id` → read `GR` body → `kv.set(\`gr:${id}\`, gr)` → `c.json({ ok: true })`.
- `DELETE /make-server-210cf10a/grs/:id` → `kv.del(\`gr:${id}\`)` → `c.json({ ok: true })`.

Wrap each handler in try/catch and return `c.json({ error }, 500)` on failure (surfaces table-missing errors clearly in `figma logs` rather than as opaque 404s).

### 2. Ensure the KV table exists

Make normally auto-provisions `kv_store_210cf10a`. If runtime calls 500 with `relation "kv_store_210cf10a" does not exist`, the user must create it once in the Supabase SQL editor (schema is in the comment at top of `kv_store.tsx`):

```sql
CREATE TABLE IF NOT EXISTS kv_store_210cf10a (
  key TEXT NOT NULL PRIMARY KEY,
  value JSONB NOT NULL
);
```

This cannot be run from here (edge deploys don't run migrations); it is a one-time manual step and will be called out to the user, not silently assumed done.

## Verification

1. Deploy/redeploy the edge function from Make settings → Supabase → Deploy edge function. It should deploy without the "no Supabase Code" error.
2. Reload the app. The store calls `api.list()` on mount; with routes present the pill should switch from **Local** to **Database** (green, `<Database>` icon in `src/App.tsx`).
3. Add a GR via the form; confirm it persists across a hard reload (data returns from `GET /grs`, not just localStorage).
4. Test Excel import (bulk), edit (PUT), delete (DELETE) round-trip.
5. If the pill stays on **Local** after deploy, check `figma logs` — a `kv_store_210cf10a` "relation does not exist" error means run the SQL in step 2, then retry.

## Note

No `create_make_theme`/aesthetic work: this is a backend-only fix, no UI redesign. The status pill and all UI already exist and are unchanged.
